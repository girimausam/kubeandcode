# Technical Notes Rules

When editing: 

- Preserve the original technical meaning, intent, and important details.
- Rewrite unclear or fragmented content into concise, natural, technically accurate Markdown.
- Organize information in a logical order so a reader can understand and apply it quickly.
- Use clear headings and subheadings to create an easy-to-scan structure.
- Prefer practical explanations over unnecessary theory or filler.
- Format commands, code, file paths, configuration, APIs, and technical values correctly using Markdown.
- Use code blocks with the appropriate language identifier whenever applicable.
- Turn procedural content into numbered steps and use bullet points for lists of concepts or options.
- Add useful sections such as Prerequisites, Steps, Examples, Notes, Common Issues, or Troubleshooting only when they improve the document.
- Preserve useful examples, commands, and implementation details; do not remove information merely to make the document shorter.
- Fix grammar, spelling, terminology, formatting, and inconsistencies.
- Remove repetition, vague statements, unnecessary introductions, and redundant explanations.
- Do not invent technical facts, commands, configuration values, or behavior that are not supported by the existing content.
- If something appears technically incorrect or ambiguous, improve its wording only when the intended meaning is clear; otherwise, flag it for clarification rather than guessing.
- Keep naming, terminology, formatting, and capitalization consistent throughout the document.
- Prefer short paragraphs and scannable sections over large blocks of text.
- Use tables only when they genuinely make comparisons or structured information easier to understand.
- Do not add motivational, promotional, or conversational filler.
- Keep documentation self-contained and focused on the technical topic.
- Never mention hackathons, competitions, exams, interview preparation, or similar contexts unless they are explicitly part of the technical subject being documented.
- Do not change the user's chosen technology, architecture, approach, or implementation unless the content itself requires correction.
- The final result should feel like polished technical documentation written by an experienced engineer: clear, concise, structured, practical, and easy to follow.
